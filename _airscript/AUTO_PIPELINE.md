# 无人值守链路 · 设计说明

> 2026-10-29 建。目标：**月底清表后再也不需要人工下载 xlsx**。
> 配套：`_kdocs/archive_snapshot.py`（Actions 侧）、`_airscript/transit_sync.js`（中转簿侧）

---

## 0. 结论先说

**现在起不用再按月下载了。** 三层独立保障，任何一层都能单独保住数据：

| 层 | 承担什么 | 存哪 | 谁维护 | 这层挂了会怎样 |
|---|---|---|---|---|
| **L1 月度快照** | 整月全量：量 + 渠道 + 大客户 + trade | GitHub `_archive/monthly/` | Actions 自动 | 无影响，L2/L3 还在 |
| **L2 最后好快照** | 最近一次「天数最多」的完整态 | GitHub `_archive/last_good.json` | Actions 自动 | 无影响 |
| **L3 中转簿** | 「量」的三层结构化 + 19 列日粒度 | WPS 在线簿 | AirScript 自动 | 无影响，L1 还在 |

**主力是 L1**：它不要求 AirScript 每天都成功 —— 只要某一次推送成功过，
git 里就有一个完整 commit，归档就把它固化下来了。

---

## 1. 根因：过去为什么非下载不可

填报簿每月 26 号清空重填。清空后，上个月的数据在金山文档里就没了。
过去唯一的保命手段是人工把 xlsx 下载到 `D:\成品油销量\日报20xx\` —— **忘一次就永久断档**。

但有个事实一直被忽略了：

> `data.json` 本身就是**当前会计月的完整快照**。
> 它含 `sale`（逐日逐站：吨/柴汽四段/升/金额/柴汽升金额）、`channels`（10 类渠道）、
> `bigcust`（15 个客户槽位）、`trade`。**25 号那一次就已经是整月全量。**

而 AirScript 用 GitHub Contents API 推送，**每一次推送都在 git 历史里留下一个 commit**。
所以快照本来就是全的，只是从来没人把它固化成文件。

`archive_snapshot.py` 干的就是这件事。

## 2. 自动运行所需的条件

### 2.1 L1 / L2 必需（只有这三条）

| # | 条件 | 怎么确认 | 缺了会怎样 |
|---|---|---|---|
| 1 | 填报簿上挂着 `read_daily.js`，5 档定时在跑 | 填报簿「驾驶舱配置」C 列有运行日志 | 没有新 data.json，归档停摆 |
| 2 | GitHub 令牌有效，写在「驾驶舱配置」B1 | 日志里没有 401 | 推送失败 |
| 3 | **Actions 有写权限** | 仓库 Settings → Actions → General → Workflow permissions → 勾 **Read and write** | `git push` 被拒，归档提交不上去 |

> ⚠️ 第 3 条最容易踩。只读权限下 Actions 能跑完构建，但最后一步 push 会 403。

**这三条齐了，清表就不再丢数据 —— 跟中转簿建没建完全无关。**

### 2.2 L3 中转簿额外需要（可选，不做也不影响 L1/L2）

| # | 条件 |
|---|---|
| 4 | 上传 `_publish/成品油经营数据中转簿.xlsx`（3.52 MB / 6 表 / 日粒度 19 列） |
| 5 | 中转簿里新建 AirScript，**「服务」里加「云文档API」**（否则 `KSDrive` 是 undefined） |
| 6 | 粘贴 `transit_sync.js` |
| 7 | 「配置」表 B2 填**填报簿**的分享链接 |

## 3. 触发方式

```
┌─ 填报簿（销售及库存日报）────────────────────────────┐
│  AirScript read_daily.js   8:30 / 9:00 / 9:30 / 10:00 / 11:30
│      ↓ 解析 + 推 data.json
└──────────────────────────────────────────────────────┘
                     ↓ GitHub Contents API（产生 commit）
┌─ GitHub Actions rebuild.yml ─────────────────────────┐
│  1. 应用 data.json                                    │
│  2. 应用 flow.json（车流，带校验）                     │
│  3. ★ 归档月度快照  ← archive_snapshot.py            │
│  4. 重建驾驶舱                                        │
│  5. 发布 index.html                                   │
│  6. ★ 提交（if: always()，build 挂了也要提交归档）     │
└──────────────────────────────────────────────────────┘

┌─ 中转簿（成品油经营数据中转簿）──────────────────────┐
│  AirScript transit_sync.js  9:10 / 9:40 / 10:10 / 11:00 / 12:00
│      跨文档读填报簿「销售日报」→ 写本簿日粒度/站级/月汇总
└──────────────────────────────────────────────────────┘
```

**为什么中转簿错开 10 分钟**：它要跨文档打开填报簿，和 `read_daily.js` 同时跑会抢文件锁。

**为什么归档排在 build 之前**：build 万一挂掉，归档已经完成了。
提交步骤加了 `if: always()` —— 页面重建失败也照样把归档 commit 上去。

## 4. 数据保留策略

| 内容 | 保留期 | 体积 | 为什么这么定 |
|---|---|---|---|
| `_archive/monthly/<会计月>.json` | **永久** | ~730 KB/月 ≈ 8.8 MB/年 | 核心资产。每次覆盖写，翻月后自然冻结在 25 号那次的完整态 |
| `_archive/last_good.json` | 仅 1 份 | ~730 KB | 防坏数据覆盖：只有天数增加才更新 |
| `_archive/months_all.json` | 永久 | 几 KB | 月索引，供 build 端直接读汇总数字 |
| `_archive/HEALTH.json` | 仅 1 份 | <1 KB | 只在**实质字段**变化时落盘，不制造无意义 diff |
| git 历史里的 `_incoming/data.json` | 永久 | 每天 5 个 commit | 回溯任意一天用 |

### 为什么不存「每日快照文件」

算过账：一份整月 data.json 约 730 KB，一天一份存 400 天就是 **290 MB**，
把仓库撑成仓库瘤 —— 而 **git 历史里本来就有**。

要取任意一天的历史快照：

```bash
git log --oneline -- _incoming/data.json          # 找 commit
git show <commit>:_incoming/data.json > day.json  # 取出那一天
```

所以只固化「整月」（核心资产）和「最后一份好数据」（保险），不重复存 git 已有的东西。

## 5. 异常处理

### 5.1 故障矩阵

| 故障 | 谁会发现 | 后果 | 怎么恢复 |
|---|---|---|---|
| 某天 AirScript 没跑成 | 次日跑时 `days_with_data` 少一天 | 少一天 | **下次自动补**：中转簿每次重写当月全部日；月初重来前都会覆盖 |
| `data.json` 读表不全（体积异常小） | `read_daily.js` 体积护栏 + 归档的回滚保护 | 已 complete 的月不被覆盖 | 自动 |
| Actions 失败 | GitHub 默认发邮件给仓库 owner | 页面不更新 | 手动 Re-run |
| 中转簿脚本挂了 | `HEALTH.json` 的 alert | 中转簿不更新 | 不影响 data.json，修好重跑 |
| 月末那天全挂 | **回溯校验**（翻月后自动） | 该月标 `incomplete` | ⚠️ 补不回来，只能认 —— 见 5.2 |

### 5.2 唯一的真风险：月末临界

**25 号那天如果 5 档全挂，26 号清表后就补不回来了。** 这是整个方案唯一没法自动兜底的场景。

缓解措施：

1. **5 档定时**（8:30 到 11:30），全挂的概率很低
2. **回溯校验会主动发现**：翻月之后，脚本会把「期末已过但天数不足」的月自动标成
   `incomplete`，并写进 `HEALTH.json` 的 alert —— 不需要人等，它自己会说
3. **人工只需要看一眼**：见到 incomplete，去 git 历史找最接近 25 号的那个 commit，
   接受缺最后一天，或回填报簿补录

### 5.3 完整性三态

```
complete    实际天数 >= 应有天数        这个月齐了
running     未到期，天数不足是正常的      月中本来就没走完
incomplete  已过期末，天数仍然不足        ★ 真丢数据了，告警
```

第三态是关键 —— 它会在**翻月之后**回头把「上个月没走完」的那些月标出来。

## 6. 为什么可以反复执行（幂等性）

三个写入点全是**覆盖式 upsert**，没有一处是「追加」：

| 写入点 | 键 | 重复跑的后果 |
|---|---|---|
| `monthly/<会计月>.json` | 会计月 | 覆盖同一文件；内容哈希没变就连写都不写 |
| `last_good.json` | 天数最多 | 只有天数变多才更新，不会退 |
| 中转簿日粒度 | 日期 + 站名 | 覆盖同一行 |
| 中转簿站级明细 | 会计月 + 站名 | 覆盖同一行 |
| 中转簿月汇总 | 会计月 | 覆盖同一行 |

**跑 1 次和跑 100 次结果完全一样。** 这不是声称，是实测过的：

| 回归场景 | 结果 |
|---|---|
| 干净首跑 → 立即再跑一次 | 四个产物文件 md5 **完全一致** |
| 把月归档伪造成 complete/31 天，用 3 天数据冲 | ✅ 拒绝覆盖，保留 31 天 |
| 造一个「期末已过仍 running」的月 | ✅ 自动翻成 incomplete 并触发 alert |
| 17 个边界用例（2 月 30/31 块、`~$` 锁文件、跨月、缺日号） | 全部通过 |

设计上刻意避开「聪明」的做法：
不用「翻月时搬一次」而用「每次覆盖当前月」—— 前者要判断"是不是刚翻月"，
一旦那天 Actions 挂了判断就错、搬移就漏。**幂等 > 聪明。**

## 7. 怎么确认它在正常工作

### 每天（顺手看一眼，10 秒）

打开 `_archive/HEALTH.json`，或者看仓库首页最新 commit 有没有 `auto: rebuild cockpit`。

### 每月 26 号以后（应该什么都不用做）

查这三行就够：

| 检查 | 期望 |
|---|---|
| `months_all.json` 里上个月的 `status` | `complete` |
| `days_count` / `expected_days` | 两者相等（如 31 / 31） |
| `HEALTH.json` 的 `incomplete_months` | `[]` 空数组 |

### 中转簿侧

「运行日志」表最后一行应该有当天的时间和「落表成功」。

## 8. 灾难恢复

### A. 填报簿丢了 / 损坏了

1. L1 的 `_archive/monthly/*.json` 里有每个月的完整 payload
2. 「量」还可以从中转簿 19 列日粒度重建（已验证：零售 332,659.9673，与源表真值一致）
3. ⚠️ 但**渠道/大客户/车流只能从 monthly 快照来** —— 中转簿只有「量」

### B. 某个历史月缺数据

```
1. 查 months_all.json 看哪个月 status=incomplete
2. git log --oneline -- _incoming/data.json | grep <那个月>
3. 找最接近月末的 commit，git show <sha>:_incoming/data.json
4. 手工放回 _incoming/data.json 推一次（归档会重新固化）
```

### C. 中转簿整本丢了

重新上传 `_publish/成品油经营数据中转簿.xlsx` 即可 —— 历史 34 个月都在文件里。
之后的增量由 `transit_sync.js` 接着写。

### D. GitHub 仓库挂了

中转簿仍在 WPS 上，19 列日粒度覆盖 2024-01 至今。
`data.json` 可以从日粒度重建「量」的部分（渠道/大客户丢失）。

## 9. 还差一步才能真正「无人值守」

L1/L2 已经做到「数据不会丢」。但 **`HEALTH.json` 本身不会主动告警** ——
它只是躺在仓库里的一个文件，没人看就等于没有。

目前唯一的主动告警是 **GitHub Actions 失败邮件**（仓库 owner 默认收到）。
它只覆盖「Actions 挂了」，不覆盖「数据不完整」这种「跑成功了但结果是坏的」情况。

要补的话有两个方向：

1. **驾驶舱首页显示健康条**（推荐）：build 时读 `HEALTH.json`，
   有 alert 就在页面顶部显示红条。用户每天都会看驾驶舱，这是最自然的告警渠道。
2. **Actions 里加一步：alert 非空就 `exit 1`** —— 让 job 失败，从而触发邮件。
   代价是页面也不重建了，不好。

方向 1 更合适，需要改 `build_cockpit2.py`（读 HEALTH）+ `cockpit2_template.html`（渲染红条）。
本轮未做。
